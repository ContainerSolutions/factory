# LLD — Effector CLI and MCP server (AGT)

> Workstream: [AGT](../../definitions.md#agt-agent) · Task: AGT-S1-T05 · Package: `internal/agent/effector`
> Ops: [contracts.md §Effect ops](../../foundation/LLD/contracts.md#effect-ops) · Server side: [api-server.md §Effector API](../../dispatcher-runtime/LLD/api-server.md#effector-api-post-tasksideffects)

## Shape

One Go implementation, two front-ends:

```go
type Effector struct { API apiclient.Client; TaskID string; Allow []string; LabelGlobs []string; Git GitOps; seq atomic.Int64 }
func (e *Effector) Do(ctx context.Context, op string, args map[string]any) (Result, error)
```

- **CLI** — `factory <op> [flags]` (the `factory` name is a symlink to `factory-agent fx` placed on the run's `PATH`).
- **MCP** — `factory-agent mcp` (stdio, `modelcontextprotocol/go-sdk`), one tool per op with a JSON Schema for its args; tool list generated from the same op table, so CLI and MCP never drift.

## Behaviour

1. **Local pre-check** (fast feedback, not security): op ∈ `Allow`, labels match globs → else exit 3 with a clear message (the server re-checks; it's authoritative).
2. **Idempotency key** = `<taskID>/<op>/<seq>`. `seq` increments per CLI/MCP call within the run and is persisted in `out/.effector-seq`, so keys stay unique across adapter restarts. On **network errors** the CLI retries the same call with the **same** key (up to 3 times), so the server applies it once. A *new* call is always a new effect, so skills must check before repeating an effect (e.g. `factory pr open` first looks up an open PR for the head branch server-side, and comments carry a skill-chosen `--key` when they must be unique per logical step: `factory comment --key plan-summary` → key `<taskID>/comment/plan-summary`).
3. API ops → `POST /tasks/{id}/effects`; print `{"effectId", "url"}` as JSON on stdout; non-2xx → exit 4 with problem detail.
4. Git ops run in `repo/` using the credential helper; after success they `POST` a record (`op`, `ref`, `sha`).
5. `lisa` compatibility: when `FACTORY_API` is set, `lib/lisa` subcommands that write to GitHub delegate to `factory …` (SKL-S1-T02 implements the delegation on the lisa side).

## Exit codes

`0` ok · `2` usage · `3` not allowed (local) · `4` server rejected / failed · `5` git failure.

## Tests

- Each op against `factory-mock` (request body golden).
- MCP: tool list equals CLI op table; a call round-trips through the same `Do`.
- Credential helper: answers only for the task's repos; nothing for others (public reads anonymous).
- Retry with same key on simulated network error.

## Decisions taken in AGT-S1-T05

- **Package and front-ends.** `internal/agent/effector`: one op table (`Ops()`, ops.go) from which both the CLI (`factory <op>`, i.e. `factory-agent fx <op>`, `effector.Main`) and the MCP server (`NewMCPServer`/`ServeMCP`) are generated, and one `Effector.Do(ctx, op, args)` behind both. `factory-agent fx` keeps its internal ops (`git-credential`, `claude-hook`) and dispatches everything else to the table; `factory-agent fx help` lists both.
- **`mcp` is both `factory-agent mcp` and `factory-agent fx mcp`**, the same server. The harnesses' MCP configs stay as AGT-S1-T03/T04 wrote them: the workspace's `bin/factory` with `["mcp"]` (`clirun.FactoryCLI` and `clirun.EffectorArgs`, unchanged), which is `factory-agent fx mcp`. That settles the question harness-adapters.md left open; no adapter change was needed.
- **MCP library.** `github.com/modelcontextprotocol/go-sdk` v1.8.0 (the allow-list's), stdio newline-delimited JSON-RPC (`mcp.IOTransport` on the process's stdin/stdout). Its transitive modules (`google/jsonschema-go`, `segmentio/encoding`, `yosida95/uritemplate`, `x/oauth2`, `x/time`) come with it. Each tool is registered with a hand-written JSON Schema (`type: object`, one property per param, `required`, `additionalProperties: false`) and a raw handler, so arguments are checked by the same parser as the CLI's flags. **Tool names** are the CLI words joined by `_` with `-` as `_` (`pr_open`, `issue_sub_add`, `stack_rebase`): OpenAI-style function names (codex) don't allow `.` or spaces. A failed op is a tool result with `isError: true`, the message and `{"error": {message, exitCode, problem?, …}}` (as text and as `structuredContent`), so the model sees why; an unknown tool is a protocol error.
- **The op table** is effector.md's table plus **`issue link-duplicate --of N [--target]`** (`link-duplicate`, the one contract op the table lacked), 19 ops. Every effect op takes an optional `--key`; every API op prints `{"effectId", "idempotencyKey", "url"?, "ref"?}` (`ref` is `owner/name#N`, parsed from an issue or pull request URL: `issue create` and `pr open` "return the ref" this way). Arg names are the GitHub adapter's (GH-S1-T04): `body`, `labels`, `title`, `issue` (sub-issue), `reason`, `duplicateOf`, `head`, `base`, `draft`, `sha`, `mergeLabel`, `commit`, `comments[]{path, line, body, side?, startLine?, startSide?}`, `thread`. CLI flags are the kebab-case param names (`--merge-label`, `--force-with-lease`), except `label add|remove --name L` (repeatable; the MCP property is `labels`). Text params (`body`) take `--body <text>` or `--body-file <path>` (`-` is stdin), JSON params (`comments`) `--comments <json>` or `--comments-file`; MCP takes the value inline only. Lists are repeatable and comma-separated. References accept `N`, `#N` (in the task's repo), `owner/name#N` and GitHub issue/PR URLs. `review --event approve|request-changes|comment` maps to `review.approve`/`review.request-changes`/`review.comment`, body required but for approve. `thread reply|resolve` take an optional `--pr` (default: the task's primary object).
- **What the CLI knows about the task: `$FACTORY_EFFECTOR`.** The pipeline now writes `<workspace>/effector.json` (0600, outside `out/`; `pipeline.EffectorConfig`, built by `pipeline.EffectorConfigFor`) and sets `FACTORY_EFFECTOR` to its path: task, TaskSpec, provider, target repo (`Target.Repo`, else the ref's repo, else the credential's), `effects.allow`, `effects.labels`, `output.outcomes`, the checkout (`repo/`) and the Result schema file. No secret is in it. The API, token, task, `out/` and `$FACTORY_RESULT` still come from the FACTORY_* variables. Without the variable (outside a run) there is no local pre-check and bare `N` references are refused.
- **Local pre-check** mirrors the dispatcher exactly: the op in `effects.allow`, and **every label the effect carries** matching `effects.labels` (`internal/patterns`), as the dispatcher checks them since factory#43: the same small op → label-args table (`labelArgs`): `label.add`/`label.remove` `labels`/`label`, `create-issue` and `pr.open` `labels`, `pr.merge`'s `mergeLabel` (when set). Exit 3 with the allowed list and the arg in the message (`label "x" (mergeLabel) is not allowed for this task (effects.labels: …); the dispatcher would refuse it too`). Git-side ops are pre-checked **before** git runs, since the server only records them.
- **Idempotency keys (a refinement of §Behaviour 2).** With `--key K`: `<task>/<op>/<K>` (K ≤ 100 chars, no spaces), as the LLD says. Otherwise **`<task>/<op>/<h>.<n>`**: `h` is the first 16 hex digits of sha256 over `{op, target, args}` (canonical JSON), `n` how many calls with that same `h` already **succeeded** in the run. The LLD's per-call `seq` would make a CLI call that the harness retries after a crash, a timeout or a lost answer a second effect; with `n` counted on success only, a call that failed or never got its answer is sent again with the same key and the dispatcher replays it, while the same command after a success is a new effect (two identical comments on purpose still work). The counts live in `$FACTORY_OUT/.effector-seq` (`{"done": {"<op>/<h>": n}}`), updated under `flock`, so CLI processes, the MCP server and adapter restarts share them; outside a run they're in memory. Concurrent identical calls get the same key, i.e. one effect. Network errors (no HTTP answer) are retried inside one call with the same key, 3 attempts with a 250 ms·attempt backoff (injectable for tests); HTTP answers are never retried by the CLI.
- **Exit codes and output.** 0 ok (JSON on stdout); 2 usage (unknown op, bad flag, missing or invalid argument, outside a task); 3 local refusal; 4 the dispatcher refused or failed, or `factory result` found problems; 5 git/gh failure. A failure prints a message on stderr and `{"error": …}` on stdout. Dispatcher answers map to: 400 "refused as invalid: <detail> (field: message)", 401 "refused the agent token", 403 "<op> is not allowed: <detail>" (effect-, label-, target-not-allowed, not-lease-holder), 404 "not found", 429 "rate limited: <detail>; retry in Ns (Retry-After) with the same arguments (the call replays)", others "failed: the dispatcher answered <status>". The problem (`status`, `code`, `detail`, `fields`, `retryAfterSeconds`) is in the JSON.
- **Git-side ops** run in `EffectorConfig.RepoDir` (else the working directory) with the run's environment, so git uses the in-memory credential helper's process-scoped `GIT_CONFIG_*`; the CLI adds `GIT_TERMINAL_PROMPT=0` and **drops `GH_TOKEN`/`GITHUB_TOKEN`** from git's environment (git never needs it). No token is ever an argument, a URL or a file. Branch names are checked (`git check-ref-format --branch`, never option-like). Runs in one process are serialised (the MCP server may get concurrent calls).
  - `factory push [--branch B] [--force-with-lease]`: `git push --porcelain [--force-with-lease=refs/heads/B] origin refs/heads/B:refs/heads/B` (B defaults to the current branch; a detached HEAD is a usage error), then records `push-branch` `{branch, ref, sha, forced?}`.
  - `factory stack push|rebase [--base B] [--git]` use **`gh stack push|rebase --remote origin`** when the checkout has gh-stack's state (`<git-common-dir>/gh-stack`) and `gh stack --help` works, with the run's environment: `GH_TOKEN` (the scoped task token, passed only through gh's environment) and the scratch `HOME`, so the owner's gh login is never used; plus `GH_PROMPT_DISABLED=1`, `GH_NO_UPDATE_NOTIFIER=1`. Otherwise (or with `--git`) the **git fallback**: `stack push` pushes the stack's branches atomically with a per-branch lease (`git push --atomic --force-with-lease=refs/heads/<b>… origin <b>:<b>…`); the branches are `--branches` (bottom first) or the local branches merged into HEAD and not into `origin/<base>` (minus the base), ordered by their distance from it. `stack rebase` fetches `origin/<base>` and runs `git rebase --update-refs origin/<base>` on the current (top) branch, which moves the branches below it too (git ≥ 2.38); on conflicts it stops, leaves the rebase in progress and says to resolve, `git rebase --continue`, then `factory stack push` (exit 5). The base defaults to `origin/HEAD`'s branch, else `main`. Both record their op `{base, via: gh-stack|git, branches, shas | onto, head, sha}`.
  - **Gap:** the run's HOME is a scratch directory, so the owner's gh extensions (gh-stack among them) aren't visible to the run's gh: in today's runs the git fallback is what runs unless the worker's PATH has a gh with gh-stack installed for that HOME. Exposing the owner's extension directory (or a configured gh-stack binary) to runs is a worker-config change for later.
- **`factory result --file f`** (MCP: `file`, or the `result` object) validates with the pipeline's own check, exported as `pipeline.ValidateResult` (the Result schema, the spec schema from `EffectorConfig.Schema` unless that file is the Result schema itself, the status, the outcome against `outcomes`, `task` matching), and copies the document unchanged to `$FACTORY_RESULT` (atomically; a file that is `$FACTORY_RESULT` is only validated). An invalid Result is exit 4 with `problems`. The pipeline still checks the file after the run.
- **Tests** (all with `-race`): every API op from the CLI against an `httptest` dispatcher (request body golden `testdata/requests.golden.json`, `-update`; path, bearer token, key format; a case per op, checked against the table) and against **factory-mock** (built and run; API ops and the three git ops' records); the idempotency scheme (same call twice → `.0`/`.1`; a 429 then the retry → same key; `--key` stable; the state file across processes; concurrent CLI and MCP callers); a dropped connection retried with the same key and an unreachable dispatcher (3 attempts); every error mapping; usage errors; the local refusals and the dispatcher's own refusal without a policy; `factory result`; git-side ops in a checkout of a private repo served by `git http-backend` that answers only the task token, through the real credential helper (the test binary), with a git wrapper logging every command line: push, a rejected non-fast-forward and `--force-with-lease`, the stack fallback (push, rebase onto a moved main, re-push, conflict), gh stack through a fake `gh` (its arguments, `GH_TOKEN` and `GH_PROMPT_DISABLED` in its environment), and no token in any argv, in git's environment or in `.git`; MCP: `tools/list` equals the op table (names, one property per param, the CLI's flags exactly those plus the `-file` variants, the required params), `tools/call` round-trips through the same `Do` (the same request as the CLI's), refusals are tool errors, raw stdio JSON-RPC over pipes, and `factory-agent fx mcp` / `factory-agent mcp` from `cmd/factory-agent`; and against the **real dispatcher** (`factory serve --dev-fake-providers`, the PoC catalog, a held plan-epic lease): create-issue, sub-issue.add and a keyed comment applied, the key replayed, the local refusals, and the dispatcher's `effect-not-allowed`, `label-not-allowed` and `target-not-allowed` without the pre-check.
