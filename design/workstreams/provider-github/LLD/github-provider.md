## Auth and tokens

```go
type Minter interface {
    Token(ctx context.Context, identity string, repos []string, perms map[string]string, ttl time.Duration) (Credential, error)
}
```

- JWT from App ID + private key (`ghinstallation`), installation ID resolved per org and cached.
- `POST /app/installations/{id}/access_tokens` with **`repositories: [name]` and `permissions: {…}`** — the body is always populated; a request without `repositories` is a programming error (`panic` in tests, error in prod) → *unscoped tokens are impossible by construction*.
- Git credentials for agents: `rw` repo token with the TaskSpec permissions (subset of the identity's), on that repo only; read repos: public ones get **no token** (`publicReads`), private ones a separate read-only token each (`contents: read`, one repo per token). The scheduler asks for each with its own `MintGitCredential` call; the request shapes and how private is decided are in [contracts.md §Refinements](../../foundation/LLD/contracts.md#refinements-fnd-s1-t03).
- Cache key `(identity, sorted repos, sorted perms)`; reuse until 5 min before expiry (GitHub caps at 1 h).
- Dispatcher-side API calls use the same minter with the identity the effect requires.

Implemented in GH-S1-T01 as `internal/provider/tokens`; the shape differs from the sketch above, see [§Decisions taken in GH-S1-T01](#decisions-taken-in-gh-s1-t01).

**Installations (group 1).** A mint that fails because the App isn't installed on the repo (the installation lookup's 404, or the token request's 422 when the owner's cached installation doesn't cover it) is a `*provider.NotInstalledError{identity, app slug, repo}` (it matches `provider.ErrNotFound`). The Conn is a `provider.InstallationChecker`: `MissingInstallations(identity, repos)` lists each owner's installation repos (`Minter.InstallationRepos`; no installation on the owner misses all its repos). `factory serve` runs `controllers.InstallationCheck` at start and on every catalog swap over `controllers.InstallationTargets`: per github Provider identity, the literal scope repos of the RuleSets (as the TaskSpecs' identities they dispatch, and as the rule identity for notify and effect rules), and the TaskSpecs' literal workspace repos, literal dispatch targets and skill sources on the git host. Each gap is a WARN and a `getCatalog` warning (`app-not-installed`); a glob scope names no repo, so it isn't checked.

## Ingress and normalisation

`Conn.Handler()` for `POST /hooks/github-public`:

1. Verify `X-Hub-Signature-256` (HMAC-SHA256, constant time) → 401 on failure. Every refusal (400, 401, 405, 413, 503) is `application/problem+json`, with the API server's shape and codes (`receiveWebhook` in `api/openapi.yaml`); 202 and 200 have no body.
2. **Accept before acknowledging:** `sink.Accept(RawEvent)` stores a `Delivery` record (`gh-<X-GitHub-Delivery>`, raw headers and body, `status: received`) in the store; a `Create` conflict means a duplicate delivery → 200 no-op. Only after the record exists does the handler return `202` (within 1 s). Normalisation runs from the store (provider controller watches `Delivery`), never from an in-process channel.
3. **Event identity is separate from delivery identity.** One delivery can normalise into several Events (e.g. `check_suite` → one per PR). Each gets `ID = gh-<delivery>/<n>` with a stable `n` (outputs sorted by object ref), so store dedupe keeps all of them.
4. **Restart gap.** The PoC store is in memory, so accepted-but-unprocessed deliveries are lost if the process dies. On startup, the provider lists the App's recent webhook deliveries (`GET /app/hook/deliveries`, covering the last 24 h) and ingests any it hasn't seen, through the same `Accept` path. State-bearing changes are additionally healed by the work-item resync (level-triggered).

## Observe and projection

`Observe(ref)` — one GraphQL query per object:

- Issue: state, labels, sub-issues, linked PRs, comments count.
- Deploy: for work items with merged PRs, the latest `github-pages` deployment of the default branch → `item.deploy{state, sha, url, containsMerge}` (`containsMerge`: every merge commit of the item's PRs is an ancestor of `sha`, via the compare API). docs' Pages workflow cancels in-progress deploys, so only the latest one matters.
- PR: `isDraft`, `headRefOid`, `baseRefName`, labels, `reviews(last:20){author, state, commit{oid}}` → `approvedBy[]{identity, commit}`, `reviewThreads(first:100){isResolved}` → `unresolvedThreads`, `commits(last:1){checkSuites(first:100){status, conclusion, checkRuns{totalCount}}}` → `checks{state, settled}`, merged/mergedAt/mergeCommit, author (factory or not).

There is no `List`, and `Observe` doesn't read the markers back: the work-item rebuild that used them is gone (P3 §No rebuild from markers), and the store is the authority. The markers and labels are for people to read. Only `Project` reads the App's own markers, to find the one it updates and which labels other work items own.

`Project(ref, p)`:

- **Marker comment** — one per (work item, object), authored by the `author` App, upserted (find by `<!-- factory:wi ` prefix, edit if digest differs):

  ```markdown
  <!-- factory:wi v=1 id=wi_01JA… state=release:drafting,train:compliance-framework%2Fworkflows%23123 runs=release-docs:1 links=github-public:compliance-framework%2Fdocs%2357 -->
  🏭 Tracked by CCF Factory — [view](https://<public-url>/workitems/wi_01JA…)
  ```

  Values URL-encoded; structured values (e.g. `plan`) as base64url JSON with prefix `b64:`; max 60 KB (else state stored only in the dispatcher and a warning logged).
- **Labels** — ensure the projection's factory-owned labels; never remove labels the factory doesn't own.

Implemented in GH-S1-T03; the details are in [§Decisions taken in GH-S1-T03](#decisions-taken-in-gh-s1-t03).

## Decisions taken in GH-S1-T01

- **`Minter.Token(ctx, provider.GitCredentialRequest) (provider.Credential, error)`**, not `Token(ctx, identity, repos []string, perms, ttl)`. Taking the request means `GitCredentialRequest.Validate` is always the first check, and one repo per token is in the type: a `Repo` string, never a list. The minter refuses (`ErrInvalid`, before any GitHub call): whatever `Validate` refuses; **any `ReadRepos`**, since #29 every read repo gets its own `ReadOnlyRequest` and a multi-repo token would also have to fit one installation; **an empty permission set**, since GitHub would then grant everything the installation has; unknown permission names or levels (`read` < `write` < `admin`); a repo that isn't `owner/name`; and an unknown identity. The access-token body is built only by a constructor that needs one repo name and at least one permission, and neither JSON field has `omitempty`. So "a request without `repositories`" can't happen, and there is no test-only `panic` (AGENTS.md: no `panic` outside `main`).
- **The identity's permissions are its installation's.** `AppIdentity` has no permission list (contracts unchanged), so the ceiling is the `permissions` GitHub reports for the installation, from the installation lookup. A request asking for more is refused locally, with the missing permissions named. If the cached installation says no, the minter looks it up again once before refusing, so a permission granted since then is seen without waiting for the cache to expire.
- **Installation lookup: `GET /repos/{owner}/{repo}/installation`**, cached per (identity, owner) for `InstallationTTL` (default 1 h). It works for organisation and user accounts alike (dev mock repos may live under a user), where `/orgs/{org}/installation` works only for organisations. The entry is dropped when the token call answers 401, 404 or 422 (App reinstalled, repo removed from the installation).
- **JWT via `ghinstallation.AppsTransport`**, as the LLD says. It is used only for its signing transport; its own installation `Transport` and token cache aren't, because they key a token by installation rather than by (identity, repo, permissions). The private key is parsed with the standard library (PKCS#1 or PKCS#8) so that a bad key fails `Connect` with an `ErrInvalid` that carries no key material. ghinstallation stamps the JWT with the wall clock (iat now−30 s, exp iat+2 min), so the JWT doesn't follow the injected clock; caches and credential expiry do.
- **Expiry.** `Credential.ExpiresAt = min(GitHub's expires_at, now + min(TTL, 1 h))`. A cached token is reused while `now < expires_at − 5 min`, whatever the new request's TTL, and its `ExpiresAt` is then bounded by GitHub's expiry. Expired entries are pruned at each mint.
- **Concurrent mints share one call** per cache key, and concurrent lookups share one per (identity, owner). The flight is written in the package because `golang.org/x/sync` isn't on the allow-list. If the caller running the call gives up (its context ends), the callers waiting on it try again under their own contexts instead of inheriting its cancellation.
- **Errors.** GitHub error responses are `*tokens.APIError{Op, StatusCode, Message (truncated), RequestID}`, and `errors.Is` maps them: 401 → `tokens.ErrUnauthorized`, 403 → `tokens.ErrForbidden` and `provider.ErrForbidden` (not a rate-limited 403), 404 → `provider.ErrNotFound`, 422 → `provider.ErrInvalid`. The provider package has no auth errors, so the two new ones live in `tokens`. These are retried, as a `*provider.RetryableError` wrapping the `APIError`: 429, a 403 that is a rate limit (`Retry-After`, `X-RateLimit-Remaining: 0` with its reset, or a "rate limit" message, with `RetryAfter` set from them), 5xx, and transport failures. The caller's own cancellation stays a context error.
- **Defence in depth.** A token whose response lists other repos than the one asked for is refused and not cached. The App clients never follow redirects, so a redirect can't carry the JWT to another host. Debug logs name the identity, repo, permissions, installation and expiry, never a token or JWT, and a test checks this.
- **Adapter skeleton (`internal/provider/github`).** `NewAdapter(Options{HTTPClient, Clock, Logger, Groups})`, with `Type() == "github"`. `Connect` validates the spec, resolves each identity's `privateKeyRef` through the `SecretResolver` and builds the minter. It makes **no GitHub call**, because the provider controller connects every Provider one after another at startup. The credential's `Host` comes from `apiURL` (`api.github.com` → `github.com`, else the GHE host), and `Provider` is the Provider's name. Methods not built yet return `provider.ErrUnsupported` with TODOs naming the task that builds them: `Recover`, `Normalise` and `ResolveGroup` are GH-S1-T02, `Observe`, `List` and `Project` are GH-S1-T03, and `Apply` is GH-S1-T04. `Handler` answers 503 until GH-S1-T02, so GitHub redelivers. The adapter isn't registered in `serve` yet (GH-S1-T04).
- **Health.** `Conn.Health()` doesn't block: it aggregates each identity's last outcome. That outcome comes from `Conn.CheckHealth(ctx)` (`GET /app` with each App's JWT, concurrently) or from a mint whose result says something about the identity: success, 401/403, or retryable. Refused requests, repos the App isn't installed on, and abandoned checks don't count. The result is `unknown` before any outcome, `ok` when every identity is fine, `down` when all fail and `degraded` in between, with a secret-free message per failing identity. `serve` should call `CheckHealth` at connect and on resync (GH-S1-T04).
- **`internal/provider/github/githubtest`** is the httptest GitHub. It verifies every App JWT (RS256 against the App's public key, at most 10 minutes of validity), records raw bodies, injects failures per route and can hold token calls (`Gate`) for the dedupe tests. GH-S1-T02..T04 extend it.
- **Dependencies:** `github.com/bradleyfalzon/ghinstallation/v2` v2.19.0, which pulls in `github.com/golang-jwt/jwt/v4` v4.5.2, `github.com/google/go-github/v88` v88.0.0 and `github.com/google/go-querystring` v1.2.0, all indirect. go-github isn't used directly yet. The newest major is v93, but ghinstallation v2.19.0 pins **v88**, so GH-S1-T02..T04 should use v88 to link one copy, unless ghinstallation moves first.

## Decisions taken in GH-S1-T02

- **Handler.** `POST` only (405 otherwise). The body is capped at 1 MB, the API server's limit (413). `X-Hub-Signature-256` must be `sha256=<64 hex>` and equal the body's HMAC-SHA256 under the webhook secret (`hmac.Equal`), or the answer is 401 and the sink isn't called. `X-GitHub-Delivery` (`[A-Za-z0-9-]{1,100}`, it becomes a store key) and `X-GitHub-Event` are required (400). Then `sink.Accept(RawEvent{ID: gh-<delivery>, Provider, Type: X-GitHub-Event, Headers, Body, ReceivedAt: clock})`, and only once it returns: 202, 200 for `ErrDuplicateDelivery`, 503 for any other error or no sink. `Authorization`, `Cookie` and `Proxy-Authorization` are dropped from the stored headers. Logs carry the delivery ID and event name, never the body (a test checks it at debug level). **`Connect` now resolves the webhook secret** (`spec.github.webhook.secretRef`) with the private keys: without one the handler can't verify anything, so a missing or empty secret fails `Connect`.
- **Event shape.** One Event per object a delivery is about, sorted by object ref (string order), `ID = gh-<delivery>/<n>`. `Subject` is the object ref, `Time` the delivery's `ReceivedAt`, `Data.Repo` always `owner/name`. Object refs: issues and PRs `owner/name#<n>` (kinds `issue`, `pr`), releases `owner/name#<tag>` (kind `release`), deployments `owner/name#d-<id>` (kind `deployment`), as in the rules fixtures. `Data.Raw` is the compacted payload (hidden from rules, as before). Facts go through a JSON round-trip, so numbers are `float64` and lists `[]any` before the store has seen them as after.
- **Facts are what the table, the CEL allow-list and the fixtures read, nothing more:** `issue{title, labels, body}` and `label`; `text`; `pr{draft, head (SHA), base (branch)}` and `label`; `review{state (lower-case), commit}`; `checks{state}` (the conclusion, lower-case); `release{tag, previousTag, semver{major, minor, patch, prerelease, bump}}` (the table's `prerelease` is inside `semver`, where the allow-list has it); `deploy{environment, sha, url}`; `train{…}`. `event.labels` (allow-list) has no source in the table and isn't set.
- **Content refs.** `contentRef` and the by-ref fields are `github://owner/name/issues/<n>#body`, `github://owner/name/pull/<n>#body`, `github://owner/name/issues/<n>#comment-<id>` (PR conversation comments too: they are issue comments) and `github://owner/name/pull/<n>#review-<id>`. A body or comment is inlined only when the actor's tier is `maintainer` or `bot` **and the sender wrote it**: a maintainer labelling someone else's issue doesn't make its body trusted.
- **Mapping details.** `issue_comment.created` on a PR has `object.kind: pr`. `check_suite.completed` **and `check_run.completed`** map to `pr.checks.completed` (the brief asked for both; `check_run` isn't in the App's events, so it only arrives if someone subscribes it), one Event per listed PR whose base repo is this repo, deduplicated; a suite with no PRs (forks) gives none. Unmapped events and actions (`ping`, `issues.edited`, `pull_request_review.dismissed`, `pull_request_review_thread`, `sub_issues`, `deployment_status` pending/in_progress, …) give no Events and no error, logged at debug: the adapter has no metrics registry yet, so the table's "(metric)" is a log line. A mapped event missing what it maps (no `issue`, a `labeled` without `label`, a repository that isn't `owner/name`, a release without a tag, a deployment without a SHA) is `ErrInvalid`; a body that isn't JSON or a delivery for another Provider too.
- **Releases.** `previousTag` is the highest release below the tag by semver (`golang.org/x/mod/semver`, on the allow-list, now a direct dependency) that is not a draft, not flagged prerelease, has no prerelease version, and has the **same component prefix**: release-please's component tags (`ccf-v3.0.0` in `helm-charts`) compare only with their component. It is read with `GET /repos/{o}/{r}/releases` (`contents: read`, up to 10 pages). `semver.prerelease` is GitHub's flag or a prerelease version. `bump` is as the CEL `semver.bump`, and `major` when there is no previous final release (a first release documents everything). A tag that isn't semver gets `release{tag}` only. **Not provided:** `release.conclusion` and `release.train`, which the cascade test catalog (not the PoC one) reads. They come from the `release-finished` `repository_dispatch`, which is neither a row of the table nor one of the App's events; adding it is a table change (a `repository_dispatch` row and the event on the App).
- **Deployments.** `success` → `deploy.succeeded`, `failure`/`error` → `deploy.failed`, other states → none. "Linked to work items" is done by **choosing the Events' objects**: the rule controller finds a work item by the event's object, so a deployment becomes one Event per merged PR it contains (the newest 20 merged PRs from `GET …/pulls?state=closed&sort=updated`, merge commit ancestor-or-equal of the deployed SHA by `GET …/compare/{merge}...{sha}` → `ahead`/`identical`; a 404 means not contained), each with that PR as object, and they reach the work items those PRs are linked to. A deployment that contains none is one Event on the deployment object. `url` is `environment_url`, else `target_url`. The token is the read identity's, `contents: read` + `pull_requests: read` on that repo.
- **Train issues (`ccf-train`).** For `issues.closed` in `Options.TrainRepos` (default `compliance-framework/workflows`), the extractor reads the JSON between `<!-- train-state` and the next `-->` (the train's `encoding/json` escapes `<`/`>`, so the JSON can't hold `-->`; CRLF bodies from web edits work too). `dryRun` defaults to `false`, `repos` to `[]`, and a body without `manifest` or with invalid JSON gives no `train` fact (not an error). Each repo is `{name, versions, bump}` in stage order; `bump` is the largest over its packages of `semver.bump(from[pkg], versions[pkg])`: the train records `from` (the release-please manifest before the train, i.e. the previous release), so **no GitHub call** is needed. A package without `from` counts as `major`, a repo that released nothing (skipped) as `none`. The extractor doesn't depend on the actor's tier: `docs-on-release-train` gates on `train:done`/`train:dry-run`, which only triagers can set.
- **Actor.** `id` `<provider>:<login>`; `isBot` `sender.type == Bot`. **The factory's Apps are recognised by their bot login `<slug>[bot]`, the slug learned once per Conn from `GET /app`** (new `tokens.Minter.App`), not from configuration; the Provider names no slugs. If that call fails, Normalise fails and the delivery is retried rather than guessing (a factory event taken for a human's would trigger the human rules). Factory actors are `isBot` too.
- **Tier.** Trust rules in the Provider's order, first match wins, matchers ANDed, a rule with none matches anyone, else `anyone` (`DefaultTier`); `workspaceMember` never matches on GitHub. `authorAssociation` uses the payload's association **only when the sender is the author** of the comment, review, PR or issue it belongs to; otherwise it's the author's and is ignored. `bots` and group membership compare logins case-insensitively. A group is matched through its member sources on this Provider with `ResolveGroup`, cached per source for the Group's `cache.ttl` (default 10 minutes). That replaces the LLD's per-user `GET /orgs/{org}/memberships/{user}`: one listing per source per TTL serves every actor, and `ResolveGroup` is needed anyway. A source that can't be resolved (unknown team or org, `userGroup`, invalid) means "not a member of it", with a warning; a GitHub failure (5xx, rate limit) is returned, so the delivery is retried instead of under-trusting. `Conn.Tier(ctx, login, association)` is exported for that.
- **`ResolveGroup`.** `orgRole admin` → `GET /orgs/{org}/members?role=admin`, `orgRole member` → `role=all` (every member); other roles `ErrInvalid`. `team: org/slug` → `GET /orgs/{org}/teams/{slug}/members`. `users` → the list. `userGroup` → `ErrUnsupported` (Slack). Unknown org or team → `ErrNotFound`; another Provider's source, none or several sources → `ErrInvalid`. Paginated (Link `rel="next"`; only its query is reused, the path stays ours), sorted, deduplicated.
- **Org token (amends a T01 decision).** Members are an organisation permission and no repository is involved, so `tokens.Minter.OrgToken(ctx, identity, org, perms)` is **the one token body without `repositories`**: its permissions must be organisation permissions from an allow-list (`members`) at `read`, so it carries no repository permission. The installation comes from `GET /orgs/{org}/installation`, sharing the per-(identity, account) cache; it's cached and deduplicated like `Token`, checked against the installation's grants, and never handed to an agent. The adapter's own reads use the **read identity**: `author` (`EventIdentity`, the App with the webhook and `members: read`), else the first identity by name.

## Decisions taken in GH-S1-T03

- **GraphQL by hand, no new dependency.** The queries are constants in `observe.go`, posted by the new `tokens.Minter.GraphQL(ctx, token, op, query, vars, out)` and decoded with `encoding/json`, rather than through `githubv4`: errors then map like every other call (HTTP errors as in T01; a response with `errors` is a `*tokens.GraphQLError`, `NOT_FOUND` → `ErrNotFound`, `FORBIDDEN` → `tokens.ErrForbidden` and `provider.ErrForbidden`, a permission problem callers can tell from a transient one, `RATE_LIMITED` → `*provider.RetryableError`), the recorded responses under `testdata/graphql` are plain JSON, and `githubtest` answers by operation name. **A response with errors fails even with partial data**: an observation missing a field could make a rule merge. The endpoint is `<api>/graphql`, or `https://<host>/api/graphql` for a GHE REST base `…/api/v3` (`tokens.GraphQLURL`). `tokens` also gained `Do` (any method with an installation token, optional body and decoding), `NextPage` (the Link `rel="next"` query), and 410 (a deleted issue) now maps to `ErrNotFound`.
- **`Observe(ref)`** is one `Observe` query on `repository.issueOrPullRequest(number)`, so a ref of the other kind (an issue ref naming a PR) is `ErrNotFound`, as the fake does, and an empty kind is filled in. Follow-up queries (`ObserveComments`, `ObserveThreads`, by node ID and cursor) read comments and review threads past the first 100, up to 10 more pages each (`ObserveComments` went with the markers' read-back: [§P3](#decisions-taken-with-p3-no-list-no-marker-read-back)). Labels (first 100), sub-issues (GitHub caps them at 100) and reviews (`last: 100`, not the LLD's 20, so an old approval isn't cut off by a chatty review) are one page.
  - Issue: state, labels, author, `subIssues` → `SubIssues`, `closedByPullRequestsReferences` (open and closed) → `LinkedPRs`, `comments.totalCount` → `Comments`.
  - PR: `isDraft`, `headRefOid`, `baseRefName`, labels, author, `mergedAt`, `mergeCommit` (only once merged). `checks` rolls up the last commit's check suites that have check runs: `failure` once one concluded failing (failure, timed out, cancelled, action required, startup failure, stale), else `pending` while one runs, else `success` (success, neutral, skipped); `settled` for `success` and `failure`; no such suite leaves `checks` empty. **Not `statusCheckRollup`** (fx/gh-observe-perms): it also covers commit statuses (`statuses: read`), which the Apps aren't granted, and check suites are what `pr.checks.completed` reports, so commit statuses don't count. `approvedBy` is each reviewer's **latest opinion** (`APPROVED`, `CHANGES_REQUESTED`, `DISMISSED`; comments and pending reviews don't change it) when it is an approval, at that review's commit, sorted. The factory's Apps map to their identity (`ccf-factory-reviewer[bot]` → `reviewer`, `ccf-factory[bot]` → `author`, from the slugs T02 learns), anyone else to their login; a deleted account counts for nobody. `unresolvedThreads` counts `isResolved: false` across all pages.
  - Author: `<provider>:<login>` with REST's spelling (GraphQL's Bot `ccf-factory` is `ccf-factory[bot]`, as in webhooks), `isBot`, and `isFactory`/`identity` for the factory's Apps; nil for a deleted account.
  - Projections (removed with P3: [§P3](#decisions-taken-with-p3-no-list-no-marker-read-back)): the v1 markers among the comments **written by the projecting App** (the author identity); a look-alike by anyone else, or a marker of another version, is ignored (the latter with a warning). Of two markers for one work item the oldest comment wins. Comment bodies are read only for that and never returned.
  - **Other kinds**, because the work-item view and the rule controller's probe treat any error but `ErrNotFound` as fatal: a `repo` link (an event without an object) is open, or closed once archived (`ObserveRepo`, `metadata: read`); releases and deployments are immutable records, `closed` with no call. Any other kind is `ErrInvalid`.
- **Deploy** is set on **merged PRs only**: the latest deployment (REST `GET …/deployments?environment=<env>&ref=<default branch>&per_page=1`) to `Options.DeployEnvironment` (default `github-pages`), its latest status's `state` (`pending` when it has none) and `environment_url` (else `target_url`), its `sha`, and `containsMerge` when this PR's merge commit is ahead-or-identical by the compare API (shared with T02's deployment linking). Observe is per object, so "every merge commit of the item's PRs" can't be computed here. **Gap for RT:** `buildView` takes `item.deploy` from the primary link, else the first link with one, so for a stack it reflects one PR; `announce-ptbr-live` should see `containsMerge` ANDed over the item's merged PRs (the controller can combine the PRs' `Deploy`).
- **Tokens and identities.** Everything is the author identity (`readIdentity`, as in T02). Observe and List read with `{issues, pull_requests, contents, checks: read}` on the object's repo (`contents` for the Commit objects the query reaches: head, merge commit, reviews' commits; `checks` for the head's check suites) (one cache key, so List's token serves the Observes that follow); the deployment with `{contents, deployments: read}`. Project reads the issue and its comments with the read token (a `pull_requests`-only token can't tell an issue from a missing one) and writes with **`issues: write` on an issue, `pull_requests: write` on a PR**, nothing else.
- **Marker format v1** (`marker.go`), as the LLD's, with what round-tripping needed: `links` are `provider:ref[:kind[:primary]]`, so the rebuild gets kinds and the primary back; a new **`labels=`** field records the factory-owned labels this work item put on the object; every key and value is percent-encoded (only `A-Z a-z 0-9 . _ ~ -` stay), so no value can hold a space, comma, colon, `>` or `-->`; non-string state values (numbers, bools, maps, lists) are `b64:` base64url JSON, and parse back as a JSON round trip gives them (`float64`, `[]any`), as the controller's state already is. Unknown fields are ignored, so v1 can grow. The visible line links to `<Options.UIBaseURL>/workitems/<id>` when the new `Options.UIBaseURL` is set (`serve` wiring is GH-S1-T04), else it has no link. Over 60 KB the marker is written without `state` and a warning is logged; still over is `ErrInvalid`.
- **`Project(ref, p)`**: (1) labels, then (2) the marker, so a failed marker write is retried with the old ownership still on record. Labels: add the projection's labels the object lacks; remove those the work item's **previous marker** owned that the projection dropped, unless another work item's marker on the object owns them too. Nothing else is ever removed, a human's `factory:stop` included. Names compare case-insensitively, as GitHub does; a 404 on removal is success. Marker: the oldest marker the author App wrote for the work item is edited (`PATCH …/issues/comments/{id}`) when its body differs, else one is created. The same projection again makes no write. Releases, deployments and repos carry no marker: projecting onto them is a no-op (the controller would otherwise fail the reconcile).
- **`List(scope)`** (removed with P3: [§P3](#decisions-taken-with-p3-no-list-no-marker-read-back)): per repo, two searches (`GET /search/issues`, 100 per page, at most 10 pages: GitHub's 1000-result cap, with a warning): `repo:<r> is:open updated:>=<now−90d>` and `repo:<r> "Tracked by CCF Factory" in:comments updated:>=<now−90d>` (the marker's visible text, rather than the hidden header, which search may not index). **The marker search is bounded by the same 90 days**, unlike the LLD: an item older than that is past the work items' retention, so rebuilding it would only retire it again. The kind comes from the result's `pull_request` key; refs are unique and sorted.
  - **Repos.** An exact `owner/name` is used as is. A glob or regex is matched against the repos the read identity's App is installed on, in the pattern's owner when that part is exact (`compliance-framework/mock-*`), else in the Provider's `scope.orgs`; an empty `scope.repos` means every repo in `scope.orgs`, and without orgs either is `ErrInvalid`. `scope.exclude` removes repos, and **the Provider's `scope.orgs` bounds everything** (the RuleSet can only narrow it). A repo the App isn't installed on is skipped with a warning, so one stale scope entry doesn't stop the rebuild.
  - **Installation repos** (amends a T01 decision). `tokens.Minter.InstallationRepos(ctx, identity, owner)` lists `GET /installation/repositories`, which needs a token not scoped to one repo, so it is the second token body without `repositories` (after T02's `OrgToken`): **`metadata: read` only**, which every installation has, cached inside the Minter and never returned; the caller gets names. The installation is found with `GET /orgs/{owner}/installation`, then `GET /users/{owner}/installation` for a user account (dev mock repos).
- **Not done here.** `server.ContentReader` (contracts.md §Refinements says the GitHub adapter must implement it) needs the untrusted bodies Observe deliberately doesn't carry; it is left to GH-S1-T04 with the `serve` wiring.
- **`githubtest`** now has an object model (`AddObject`, `Object`, `UpdateObject`: issues and PRs with labels, author, state and comments) behind `GET /repos/{o}/{r}/issues/{n}`, its comments (list, create as the token's App bot, edit), labels (add, remove), `GET /search/issues` (the qualifiers List uses), deployments and their statuses (`AddDeployment`), `GET /installation/repositories` (`AddAccountRepos` for all-repo installations), `GET /users/{u}/installation` (`Installation.User`), and `POST /graphql`: canned responses per operation and variables (`SetGraphQL`, for recorded ones), else answered from the model. P3 §No rebuild from markers removed the work-item rebuild, the only reader of `List` and of `Observation.Projections` (stack 5, PR 6). The store is the authority; the markers and labels stay, for people to read.

## Decisions taken in GH-S1-T04

- **One token per op, the request's identity, minimal permissions on the one target repo.** `Apply` acts as `EffectRequest.Identity` (empty: the author identity; unknown: `ErrInvalid`). Comments, labels, close and link-duplicate use `issues: write` on an issue and `pull_requests: write` on a PR (the reviewer App has no `issues: write`, and the issues API accepts either); create-issue and sub-issue.add `issues: write`; pr.open/update/retarget, the reviews and the threads `pull_requests: write`; pr.merge `contents: write` + `pull_requests: write`. Nothing else is ever asked for (the tests assert every token request). **The review ops act only as `reviewer`** (`ErrInvalid` otherwise), as contracts.md's table says. Targets of kind `channel` or `group` (the rule controller's notify destinations) are `ErrUnsupported`: GitHub has neither.
- **Idempotency, per op.** What an op creates carries `<!-- factory:effect <key> -->` (the key percent-encoded like the projection marker's values, so a rule key such as `evt/<event>/<rule>/<i>` can't break out of the comment) and is looked up before creating; **only what the acting App wrote counts**, so a human pasting the marker can't suppress the factory's write. Comments: the target's comments (up to 30 pages). create-issue: **the App's newest issues, `GET …/issues?creator=<bot>&state=all&sort=created&direction=desc` (3 pages), not the LLD's `in:body` search**, because search is eventually consistent and a replay seconds later could miss the issue it created. pr.open: the open PR for the head (`GET …/pulls?state=open&head=<owner>:<head>`): GitHub allows one, so the App's is the replay and anyone else's is `ErrInvalid`. Reviews: the PR's reviews (10 pages). thread.reply: the thread's last 100 comments. Everything else reads the object first and writes only what differs: labels (case-insensitive), sub-issue links (and a 422 "already" as success), state, title/body, base, merged, resolved. **`Replayed` means "found already done, wrote nothing"**: for naturally idempotent ops the adapter can't tell its own earlier write from the same state reached otherwise. link-duplicate is a replay only when all three steps (comment, `duplicate` label, close as `not_planned`) were already done.
- **Args** (the contract left them open; the Effector passes the agent's through): `comment`/`pr.comment` `body`; `label.add`/`label.remove` `labels` and/or `label` (as the Effector checks them); `create-issue` `title` (required), `body`, `labels`; `sub-issue.add` `issue` (`owner/name#n`, `#n`, `n` or a number; same repo, since the token is on one repo); `close` `reason` (`completed`, `not_planned`); `link-duplicate` `duplicateOf` (same forms; any repo, it is only text); `pr.open` `head`, `base`, `title` (required), `body`, `draft`, `labels`; `pr.update` `title` and/or `body` (the effect markers already in the body, pr.open's among them, are kept); `pr.retarget` `base`; `pr.merge` `sha` (default: the current head), `mergeLabel`; the reviews `body` (required but for an approval), `commit` (default: the head), `comments[]{path, line, body, side?, startLine?, startSide?}`; the threads `thread` (the review thread's node ID; checked to be on the target PR, `ErrInvalid` otherwise) and, for a reply, `body`. A body over 65 536 bytes with its marker is `ErrInvalid`.
- **pr.merge.** The method is the repo's: the first of squash, merge, rebase that `GET /repos/{o}/{r}` allows (none: `ErrInvalid`). Already merged (read first, or a 405 "already merged") is a replay. A 405 whose message is about reviews (branch protection's "approving review is required", a ruleset's "Review required", code owners) is the **Q5 fallback: `args.mergeLabel` is added and the outcome is `labelled-for-merge`** (a replay when the label was there); without `args.mergeLabel` it is refused. **The merge label comes from the request, not configuration**: the Provider spec has no field for a repo's merge label (that is a contracts change), and the merge skill already takes it as a repo-config input. Refusals are a `*github.MergeError` matching `ErrMergeBlocked` (405, a closed PR), `ErrReviewRequired` (also `ErrMergeBlocked`) or `ErrHeadChanged` (409), and always `provider.ErrInvalid`, so the Effector answers 400 rather than 502. A replay after the fallback tries the merge again (it may succeed once a human approved) rather than trusting the label.
- **Retries.** A `*provider.RetryableError` (429, a rate-limited 403, 5xx, transport) **retries the whole op, lookup included**, so a write GitHub made before failing is found instead of repeated; up to 5 tries, waiting `Retry-After` or the primary limit's `X-RateLimit-Reset` when GitHub gives one, else 1 s doubling, on the injected clock. A hint over 1 minute isn't slept on: the error goes back with its `RetryAfter` (the Effector's `429` + `Retry-After`; the rule controller retries the reconcile). So does the last failure. 404 is `ErrNotFound`, 422 `ErrInvalid`, an issue ref naming a PR `ErrNotFound` (as Observe and Project), and a PR op on an issue ref `ErrInvalid`.
- **`server.ContentReader`** (`content.go`): read with the read identity's Observe token. An object ref (`owner/name#n`) gives Markdown: `# <title>`, the body, then each conversation comment headed `@<login> commented:`; the factory App's projection markers are left out, and **every `<!-- factory:… -->` marker is stripped from every text, whoever wrote it**, so no marker reaches an agent (or gets copied back). Other hidden HTML is left for the agent's fence, as the API says. Content refs give one text: `…/issues/<n>#body` and `…/pull/<n>#body`, `#comment-<id>` (checked to belong to that issue) and `…/pull/<n>#review-<id>`. `Author` is the login that wrote it; the media type `text/markdown`; a whole object is capped at 512 KB, later comments counted in a note. A ref that names no GitHub object or content (an inlined trusted fact) gives empty content, so the item stays reference-only, rather than failing the request. The adapter now imports `internal/server` for the interface's types (no cycle: the server doesn't import the adapter).
- **`factory serve`.** `adapters()` registers the GitHub adapter unless `--dev-fake-providers` (both claim type `github`), with `UIBaseURL` = `--public-url` and the new **`--deploy-environment`** (default `github-pages`, must not be empty). `CheckHealth` runs **whenever the adapter connects a Provider** (a wrapper around `Connect`: startup and every reconnect after a catalog change) and **on every catalog change for every connected Provider** (a `provider-health` component following the catalog), bounded by 15 s and logged; a failing check fails nothing, the API's provider health reports it. Without the fake, a catalog Provider whose secrets aren't set fails startup naming the variable (`TestServeGitHubProviderNeedsSecrets` replaces `TestServeUnknownProviderType`).
- **Gap for RT.** The Effector checks only `label.add`/`label.remove` against `effects.labels`, so `pr.merge`'s `args.mergeLabel` is unchecked: a merge task can add any one label to its PR when review requirements block the merge. The Effector should check `mergeLabel` against `effects.labels` like the label ops (or the merge label should become Provider configuration).
- **`githubtest`** now models issue and PR title, body, id, state reason, head branch, sub-issues, reviews (with inline comments), review threads and merge blocks (`MergeBlock`: `MergeReviewRequired`, `MergeNotMergeable`), repo settings (`SetRepo`: merge methods, default branch), and serves `GET /repos/{o}/{r}`, issue list (`creator`, `state`, `direction`), create and update, a single comment, sub-issues (list, add), PR get/create/update, open PRs by head, merge (method allowed, `sha` at head, 405/409 as GitHub), reviews (list, get, create; no self-approval) and the GraphQL `ApplyThread`, `ApplyThreadReply` and `ApplyResolveThread` (mutations are now answered too). Every route checks the token's repo and permission, the merge both `contents` and `pull_requests` write. `html_url`s are under `githubtest.WebURL`.
- **Tests.** Every op against `githubtest`: what it wrote, the token it used, and **a replay with the same key that writes nothing** and returns the same object and URL with `Replayed`; a forged marker by a human; the merge fallback (blocked → label → replay → merged once unblocked), the refusals and the method choice; retries on the fake clock (`Retry-After`, `X-RateLimit-Reset`, 5xx backoff, the bound, a long `Retry-After` returned, cancellation); refused requests with their errors; `ReadContent` for every ref form, the marker stripping and the errors; and **`TestServeGitHubEndToEnd`**: `factory serve` without `--dev-fake-providers` on the PoC catalog pointed at `githubtest`, health checked at connect, a signed `issues.opened` (202, redelivery 200, a bad signature 401) → a plan-epic Task → a fake agent leases it (a real scoped installation token), reads its context (fenced, no markers), creates and links a sub-issue and comments through the Effector (the replay by key writes nothing), completes it, and the comment, the sub-issue, the projection marker and build-stack-start's epic-plan notification land in `githubtest`; no secret or token in the logs.
