# Factory web UI

The Vue app the dispatcher embeds (`go build -tags webui`). The design is
[`design/workstreams/web-ui/LLD/web-ui.md`](../design/workstreams/web-ui/LLD/web-ui.md). The
stack and conventions follow `compliance-framework/ui`: Vue 3, Vite, TypeScript, Pinia, Vue
Router, PrimeVue (unstyled, through the Volt wrappers in `src/volt/`) and Tailwind v4.

Node 20 (`.nvmrc`) and npm. Backend work never needs any of this: without `-tags webui` the
binary embeds a placeholder page.

## Commands

```sh
npm ci
npm run dev:mock         # dev server over the MSW mocks of ../api/examples; no dispatcher needed
npm run dev              # dev server proxying /api to a local `factory serve` (FACTORY_API_URL, default http://127.0.0.1:8080)
npm run reviewable       # generated-code check + format check + lint + unit tests + type-check + build: what CI runs
npm run gen:api          # regenerate src/api/schema.d.ts and src/mocks/operations.gen.ts from ../api/openapi.yaml
npx vitest run src/App.spec.ts   # one spec
npm run build            # type-check + vite build into ../internal/webui/dist (gitignored)
```

`make build-release` at the repo root runs `npm ci && npm run build` here, then builds the
binaries with the UI embedded.

## The API client

`src/api/schema.d.ts` is generated by `openapi-typescript` from the contract,
`../api/openapi.yaml`, and `src/api/client.ts` wraps it with `openapi-fetch`. The generated
files are committed, like the Go side's generated code, and `npm run reviewable` fails when
they are stale (`npm run gen:api:check`): after a contract change, run `npm run gen:api` and
commit the result. Never edit them by hand.

## Mocks

`src/mocks/` serves every operation of the contract with its example from `../api/examples`,
at the operation's success status and media type (`src/mocks/operations.gen.ts`, generated
with the client). `src/mocks/workitems.ts` overrides `GET /workitems` and `GET /workitems/{id}`
with a few more work items built around the examples, so the board has every lane, several
providers, repos and RuleSets, and an unknown work item answers 404. `src/mocks/runs.ts` does
the same for `GET /runs/{id}` (one run is still going) and its transcript. They are dated around
2026-10-19, which the specs and the e2e test fix as "now". The unit tests run against the same handlers (`msw/node`, set up in
`vitest.setup.ts`; an unmatched request fails the spec), and `npm run dev:mock` runs them in
the browser through MSW's service worker, which the dev server serves from the msw package
(it is never copied into the build).

## Live updates

`useStream(topics, handlers)` (`src/composables/useStream.ts`) subscribes to `GET /stream`
with an `EventSource`: the board to `workitems`, the run view to `runs/<id>` and `tasks`. The
browser retries a dropped stream itself and resumes with `Last-Event-ID`; when it gives up, the
stream is re-created with backoff and the view reloads what it shows, since a new `EventSource`
can't send `Last-Event-ID`. In `npm run dev:mock`, `src/mocks/stream.ts` serves the stream per
topic: the contract's `streamEvents` example, then the running mock run's progress a frame at a
time. Node has no `EventSource`, so the specs inject a fake one (`src/__tests__/eventSource.ts`)
through `eventSourceKey`.

## End-to-end tests

Playwright specs live in `e2e/` and run over `npm run dev:mock`. They need a browser, so they
are not part of `npm run reviewable`. Install Playwright's Chromium once, then run them:

```sh
npx playwright install chromium
npm run test:e2e
```

Or use an installed Google Chrome instead: `PLAYWRIGHT_CHANNEL=chrome npm run test:e2e`.
